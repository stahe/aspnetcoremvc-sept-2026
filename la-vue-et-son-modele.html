    4. La vue et son modèle

    Jusqu'ici, les actions fabriquaient elles-mêmes leur réponse. Dans une application MVC, c'est le rôle d'une vue : un fichier qui décrit la page HTML, avec des emplacements pour les données que lui transmet l'action, le modèle de la vue. [ASP.NET Core MVC] utilise le moteur de vues [Razor] : une vue est un fichier [.cshtml], du HTML dans lequel on insère du code [C#] précédé du caractère [@]. [Razor] fait partie du framework : il n'y a rien à installer.

    using Exemple13.Models;
using Microsoft.AspNetCore.Mvc;

namespace Exemple13.Controllers;

public class VuesController : Controller
{
    // View(modèle) : la vue qui porte le nom de l'action (Views/Vues/Index.cshtml)
    [HttpGet("/")]
    public IActionResult Index()
    {
        var modele = new PageModele(
            "Ma première vue",
            "Cette page a été fabriquée par Razor, sur le serveur.",
            DateTime.Now.ToString("HH:mm:ss"));
        return View(modele);
    }

    // View(nom, modèle) : la vue est choisie par l'action
    [HttpGet("bonjour/{nom}")]
    public IActionResult Bonjour(string nom)
    {
        if (nom == "inconnu")
        {
            Response.StatusCode = 404;
            return View("Inconnu", nom);
        }
        var modele = new PageModele(
            $"Bonjour {nom}",
            "Cette fois, l'action a désigné la vue par son nom.",
            DateTime.Now.ToString("HH:mm:ss"));
        return View("Index", modele);
    }
}

    Commentons ce code :

    • ligne 6 : le contrôleur dérive de la classe [Controller], et non plus de [ControllerBase] : [Controller] ajoute à [ControllerBase] tout ce qui concerne les vues (méthode [View], [ViewData], [TempData]...) ;
    • lignes 12-15 : l'action fabrique le modèle de la vue : un titre, un message et l'heure courante ;
    • ligne 16 : [View(modele)] rend un [ViewResult] : l'action ne fabrique plus la réponse, elle désigne une vue et lui transmet un modèle. Sans nom de vue, c'est la vue qui porte le nom de l'action qui est utilisée : [Index] ;
    • lignes 23-26 : quand la vue dépend de la requête, l'action choisit la vue. Ici, le nom [inconnu] affiche la vue [Inconnu], avec le code 404. Le modèle de cette vue est une simple chaîne de caractères ;
    • ligne 32 : l'action [Bonjour] désigne explicitement la vue [Index] par son nom : deux actions partagent la même vue, avec des modèles différents.

    • [Views/Vues/Index.cshtml] : le dossier qui porte le nom du contrôleur (sans le suffixe [Controller]) ;
    • [Views/Shared/Index.cshtml] : le dossier des vues partagées par tous les contrôleurs (cf. exemple 15).

    Commentons ce code :

    • lignes 2-5 : un bloc de code [@{ ... }] contient des instructions [C#]. Il ne produit rien dans la page. Les variables qu'il déclare ([total], [nombre]) sont utilisables dans la suite de la vue ;
    • ligne 16 : une valeur [null] ([@Model.Surnom]) n'affiche rien, sans erreur ;
    • lignes 18-19 : une expression [@...] échappe les caractères spéciaux du HTML ([<] devient [&lt;]...) : le texte s'affiche tel quel. [@Html.Raw(...)] l'insère sans échappement : il est interprété comme du HTML. On n'utilise [Html.Raw] que pour du HTML fabriqué par l'application, jamais pour une donnée saisie par un utilisateur : celui-ci pourrait injecter du HTML, voire du [JavaScript], dans la page (attaque dite [XSS], [cross-site scripting]) ;
    • lignes 21-27 : une condition. Après [@if (...)], le contenu des accolades est du HTML : [Razor] reconnaît le début d'une balise et repasse en mode HTML. On revient au [C#] par [@] ;
    • lignes 32-40 : une boucle [for] [C#]. [var produit = ...] est une instruction [C#], [<li>] du HTML : [Razor] alterne les deux sans marque particulière ;
    • ligne 36 : une expression explicite [@( ... )]. Les parenthèses sont nécessaires dès que l'expression contient des espaces ou des opérateurs (ici l'opérateur conditionnel [? :]) ;
    • ligne 37 : pour écrire du texte sans balise dans un bloc [C#], on l'entoure de la balise spéciale [<text>], qui n'apparaît pas dans la page ;
    • ligne 38 : [@:] fait la même chose pour le reste de la ligne ;
    • lignes 45-51 : le cas de la liste vide est un simple [if]. Dans le bloc [else], déjà en mode [C#], [foreach] s'écrit sans [@] ;
    • ligne 55 : les variables du bloc [@{ }] et des expressions explicites, dont un appel de méthode : [ToString("0.00")] formate un nombre avec deux décimales ;
    • ligne 56 : un chemin pointé [@Model.Adresse.Rue], et un appel de méthode [ToUpper()] ;
    • ligne 57 : [Razor] sait qu'un [@] placé entre deux caractères alphanumériques n'est pas du code : [contact@exemple.fr] est une adresse électronique. Pour écrire un [@] qui serait ambigu, on le double : [@@].

using System.Text.Unicode;
using Microsoft.Extensions.FileProviders;

var builder = WebApplication.CreateBuilder(args);

// < > & " ' restent échappés

var app = builder.Build();

    Commentons ce code :

    • ligne 9 : le service [HtmlEncoder] est celui qu'utilise [Razor] pour échapper les expressions [@]. Par défaut, il ne laisse passer que les caractères de l'alphabet latin de base : c'est ce qui codait [é] en [&#xE9;]. On remplace ce service par un encodeur qui laisse passer tous les caractères ([UnicodeRanges.All]). Les caractères dangereux ([<], [>], [&], ["], [']) restent échappés : la protection contre l'injection de HTML est intacte. Tous les exemples suivants, et l'étude de cas, ont cette ligne ;
    • ligne 14 : un middleware (cf. chapitre 7) qui sert les fichiers du dossier [wwwroot] du projet : le fichier [wwwroot/css/styles.css] est servi à l'URL [/css/styles.css]. Si le fichier n'existe pas, la requête continue son chemin vers les contrôleurs ;
    • lignes 16-19 : un second service de fichiers statiques. Le framework CSS [Bootstrap] est commun à tous les exemples : il est rangé une seule fois, dans le dossier [exemples/commun/bootstrap], et servi sous le préfixe [/bootstrap]. [PhysicalFileProvider] désigne un dossier du disque ; [ContentRootPath] est le dossier du projet. Ainsi, [exemples/commun/bootstrap/css/bootstrap.min.css] est servi à l'URL [/bootstrap/css/bootstrap.min.css]. L'étude de cas, elle, range [Bootstrap] dans son propre dossier [wwwroot].

using System.Text.Encodings.Web;
using Microsoft.AspNetCore.Html;

namespace Exemple16.Aides;

// des fonctions C# ordinaires, appelables depuis les vues : @Formats.Monnaie(...)
public static class Formats
{
    // "clavier" -> "CLAVIER"
    public static string Majuscules(string? texte) => (texte ?? "").ToUpperInvariant();

    // un montant dans une devise, au format de la langue courante (CultureInfo.CurrentCulture)
    // "C" = currency ; l'objet NumberFormatInfo fixe le symbole de la devise
    public static string Monnaie(decimal montant, string devise = "EUR")
    {
        var format = (NumberFormatInfo)CultureInfo.CurrentCulture.NumberFormat.Clone();
        format.CurrencySymbol = devise == "USD" ? "$" : "€";
        return montant.ToString("C", format);
    }

    // une date en toutes lettres, dans la langue courante : "mercredi 23 septembre 2026"
    public static string Date(DateTime quand) => quand.ToString("D", CultureInfo.CurrentCulture);

    // un helper qui fabrique du HTML : il rend un IHtmlContent, que Razor n'échappe pas.
    // C'est alors au helper d'échapper les données qu'il insère (HtmlEncoder)
    public static IHtmlContent Badge(int stock)
    {
        var classe = stock > 0 ? "text-bg-success" : "text-bg-danger";
        var texte = HtmlEncoder.Default.Encode(stock > 0 ? $"{stock} en stock" : "épuisé");
        return new HtmlString($"<span class=\"badge {classe}\">{texte}</span>");
    }
}

    }
}

    4.7.1. La validation par le navigateur

    Les attributs [required], [maxlength], [min], [max], [type="email"]... demandent au navigateur de vérifier le formulaire avant de l'envoyer : l'utilisateur est prévenu immédiatement, par une bulle d'aide, sans aller-retour avec le serveur. L'étude de cas, elle, garde les deux : les attributs HTML5 pour le confort, et la validation serveur pour la sûreté.

    4.8. Exemple 20 : le schéma Post / Redirect / Get

    Quand un formulaire POST réussit, l'action peut afficher directement une page. Le problème apparaît si l'utilisateur recharge ensuite cette page (touche F5) : le navigateur renvoie le formulaire, et l'opération est faite une seconde fois (une commande passée deux fois, un rendez-vous pris deux fois...). Le schéma Post / Redirect / Get (PRG) évite ce problème : une action POST réussie ne fabrique pas de page, elle redirige vers une page GET. Recharger cette page ne refait qu'un GET, sans effet.

    Reste un détail : la page GET doit afficher un message (« la tâche a été ajoutée »), alors que ce message a été produit par l'action POST, dans une autre requête. [ASP.NET Core] fournit pour cela [TempData] : un dictionnaire dont le contenu survit jusqu'à la requête suivante, et disparaît dès qu'il a été lu. C'est un message flash. Par défaut, [TempData] est conservé dans un cookie, chiffré par le serveur.

    [

    ];

    public Contact? Modifier(int id, string nom, string telephone)
    {
        var index = contacts.FindIndex(c => c.Id == id);
        if (index < 0) return null;
        // un record est immuable : on le remplace par une copie modifiée (with)
        contacts[index] = contacts[index] with { Nom = nom, Telephone = telephone };
        return contacts[index];
    }

    {
        var contact = new Contact(++dernierId, nom, telephone);
        contacts.Add(contact);
        return contact;
    }

    public Contact? Supprimer(int id)
    {
        var contact = Lire(id);
        if (contact is not null) contacts.Remove(contact);
        return contact;
    }

    // confirmation des formulaires portant l'attribut data-confirmation="..."
// Sans JavaScript, ces formulaires partent simplement sans confirmation.
(() => {
  const modale = document.getElementById('modale-confirmation');
  const message = document.getElementById('modale-confirmation-message');
  let enAttente = null; // le formulaire à envoyer si l'on confirme

  // 1. on intercepte l'envoi des formulaires à confirmer
  document.querySelectorAll('form[data-confirmation]').forEach((formulaire) => {
    formulaire.addEventListener('submit', (evenement) => {
      evenement.preventDefault(); // l'envoi est suspendu
      enAttente = formulaire;
      message.textContent = formulaire.dataset.confirmation;
      modale.classList.remove('d-none'); // la fenêtre apparaît
    });
  });

  // 2. les deux boutons de la fenêtre
  modale.addEventListener('click', (evenement) => {
    const action = evenement.target.dataset.action;
    if (action === 'oui') {
      enAttente.submit(); // envoi, SANS redéclencher l'événement 'submit'
    } else if (action === 'non') {
      modale.classList.add('d-none');
      enAttente = null;
    }
  });
})();
    • ligne 3 : le code est enveloppé dans une fonction exécutée aussitôt, pour ne pas créer de variables globales ;
    • lignes 9-14 : on intercepte l'envoi de chaque formulaire qui porte l'attribut [data-confirmation]. [preventDefault()] suspend l'envoi ; on mémorise le formulaire, on place la question dans la fenêtre ([textContent], et non [innerHTML] : la question est affichée comme du texte, jamais interprétée comme du HTML) et on affiche la fenêtre ;
    • lignes 19-25 : « Oui » envoie le formulaire mémorisé. La méthode [submit()] d'un formulaire l'envoie sans déclencher l'événement [submit] : il n'y a pas de nouvelle demande de confirmation. « Non » cache la fenêtre.

    Si le [JavaScript] est désactivé, les formulaires partent simplement sans confirmation : l'application fonctionne toujours. C'est le principe d'amélioration progressive : le [JavaScript] ajoute un confort, il n'est pas indispensable. L'étude de cas suit ce principe (son script [wwwroot/js/app.js] ajoute la gestion du clavier : touche Échap, focus).
