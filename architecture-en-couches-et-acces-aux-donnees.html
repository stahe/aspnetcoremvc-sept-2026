    9. Architecture en couches et accès aux données

    Les exemples précédents gardaient leurs données en mémoire. Une vraie application les garde dans une base de données, et s'organise en couches (cf. schéma de l'introduction) :

    • la couche web (contrôleurs, vues) : lire la requête, appeler la couche métier, choisir la vue ;
    • la couche métier : les règles de gestion ;
    • la couche DAO ([Data Access Object]) : les requêtes à la base de données.

    Chaque couche ne connaît que la couche du dessous, et le moins possible de ses détails : la couche web ignore le SQL, la couche métier ignore le HTML. Cette séparation rend chaque couche plus simple à comprendre, à tester et à faire évoluer. L'exemple 28 l'applique à la gestion d'une liste de personnes : c'est, en plus petit, la gestion des médecins et des clients de l'étude de cas.

    L'accès à la base est confié à Entity Framework Core (EF Core), l'ORM ([Object-Relational Mapper]) de [.NET] : il fait correspondre des classes [C#] (les entités) aux tables de la base, traduit en SQL les requêtes écrites en [LINQ], et transforme les lignes lues en objets. EF Core dialogue avec chaque type de base par un fournisseur ([provider]) : pour [MySQL], le paquet [NuGet] [Pomelo.EntityFrameworkCore.MySql], qui apporte avec lui EF Core et le pilote [MySqlConnector].

  version INT NOT NULL DEFAULT 1,

  nom VARCHAR(30) NOT NULL,
  age INT NOT NULL,

    using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

namespace Exemple28.Entities;

// une ligne de la table [personnes]
[Table("personnes")]
public class Personne
{
    // la clé primaire : une clé entière est, par convention, générée par la base
    // (AUTO_INCREMENT) ; EF Core relit sa valeur après chaque INSERT
    [Key]
    [Column("id")]
    public int Id { get; set; }

    // le verrou optimiste : chaque UPDATE porte la condition "AND version = <valeur lue>"
    [Column("version")]
    [ConcurrencyCheck]
    public int Version { get; set; } = 1;

    [Column("prenom")]
    [MaxLength(30)]
    public string Prenom { get; set; } = "";

    [Column("nom")]
    [MaxLength(30)]
    public string Nom { get; set; } = "";

    [Column("age")]
    public int Age { get; set; }
}
    • ligne 7 : la classe [Personne] correspond à la table [personnes] : chaque ligne de la table sera un objet [Personne] ;
    • lignes 12-14 : la clé primaire ([[Key]]). [[Column]] donne le nom de la colonne correspondant à chaque propriété ;
    • lignes 18-19 : la colonne de version. [[ConcurrencyCheck]] demande à EF Core d'ajouter à chaque [UPDATE] la condition [AND version = <valeur lue>] : c'est le verrou optimiste, expliqué plus loin ;

    using Exemple28.Entities;
using Microsoft.EntityFrameworkCore;

namespace Exemple28.Data;

// le DbContext : la connexion à la base, et le suivi des entités lues
public class PersonnesDbContext(DbContextOptions<PersonnesDbContext> options) : DbContext(options)
{
    // la "table" des personnes : on l'interroge avec LINQ
    public DbSet<Personne> Personnes => Set<Personne>();

    // juste avant chaque enregistrement : la version de toute personne
    // MODIFIÉE est augmentée de 1. L'UPDATE généré compare l'ANCIENNE valeur :
    //   UPDATE personnes SET ..., version = 2 WHERE id = 1 AND version = 1
    public override Task<int> SaveChangesAsync(bool acceptAllChangesOnSuccess, CancellationToken cancellationToken = default)
    {
        foreach (var entree in ChangeTracker.Entries<Personne>())
        {
            if (entree.State == EntityState.Modified)
            {
                entree.Entity.Version++;
            }
        }
        return base.SaveChangesAsync(acceptAllChangesOnSuccess, cancellationToken);
    }
}
    • ligne 7 : le DbContext est l'objet central d'EF Core. Il représente une session de travail avec la base : il ouvre les connexions, envoie les requêtes, et suit les entités qu'il a lues (il sait lesquelles ont été modifiées) ;
    • ligne 10 : un [DbSet<Personne>] représente la table : on l'interroge avec [LINQ], on y ajoute des entités ;
    • lignes 15-24 : [SaveChangesAsync] envoie à la base toutes les modifications en attente. On la redéfinit pour augmenter la version de chaque personne modifiée. [ChangeTracker] est le suivi des modifications : pour chaque entité suivie, il connaît son état ([Added], [Modified], [Deleted], [Unchanged]). EF Core, contrairement à [TypeORM], ne gère pas lui-même une colonne de version entière : c'est à nous de l'augmenter.

    using Exemple28.Data;
using Exemple28.Entities;
using Microsoft.EntityFrameworkCore;

namespace Exemple28.Dao;

// la couche DAO : des requêtes, aucune règle de gestion
public class PersonnesDao(PersonnesDbContext db)
{
    // SELECT ... FROM personnes ORDER BY nom, prenom
    public Task<List<Personne>> ListerAsync() =>
        db.Personnes.AsNoTracking().OrderBy(p => p.Nom).ThenBy(p => p.Prenom).ToListAsync();

    // SELECT ... FROM personnes WHERE id = @id LIMIT 1 ; null si absente
    public Task<Personne?> LireAsync(int id) =>
        db.Personnes.FirstOrDefaultAsync(p => p.Id == id);

    // une personne de mêmes prénom et nom, autre que [saufId]
    public Task<Personne?> HomonymeAsync(string prenom, string nom, int saufId) =>
        db.Personnes.FirstOrDefaultAsync(p => p.Prenom == prenom && p.Nom == nom && p.Id != saufId);

    // INSERT si la personne est nouvelle (Id = 0), UPDATE des colonnes modifiées sinon
    public async Task<Personne> SauvegarderAsync(Personne personne)
    {
        if (personne.Id == 0)
        {
            db.Personnes.Add(personne);
        }
        await db.SaveChangesAsync();
        return personne;
    }

    // DELETE FROM personnes WHERE id = @id, sans lire la personne d'abord
    public Task SupprimerAsync(int id) =>
        db.Personnes.Where(p => p.Id == id).ExecuteDeleteAsync();
}
    • ligne 8 : le DAO reçoit le [DbContext] par injection ;
    • lignes 11-12 : une requête [LINQ], traduite en SQL par EF Core. Rien n'est envoyé à la base avant l'appel de [ToListAsync], qui exécute la requête et rend la liste. [AsNoTracking()] indique que ces entités ne seront pas modifiées : le [DbContext] n'a pas à les suivre ;
    • lignes 15-16 : la première personne qui vérifie la condition, ou [null] ;
    • lignes 19-20 : une personne de mêmes prénom et nom, autre que [saufId] : utile pour la modification d'une fiche, qui ne doit pas se trouver en conflit avec elle-même. La comparaison est faite par [MySQL], donc selon la collation de la base : sans tenir compte des majuscules ni des accents ;
    • lignes 23-30 : une nouvelle personne ([Id] à 0) est ajoutée au [DbSet] ; [SaveChangesAsync] fait alors un [INSERT], et relit l'identifiant attribué par la base. Une personne lue par ce même [DbContext] et modifiée est détectée par le suivi des modifications : [SaveChangesAsync] fait un [UPDATE] des seules colonnes modifiées ;
    • lignes 34-35 : [ExecuteDeleteAsync] envoie directement un [DELETE] à la base, sans lire les personnes d'abord.

    La couche DAO ne contient aucune règle : seulement des requêtes. Ces méthodes sont asynchrones ([Task], [async] / [await]) : pendant que la base travaille, le fil d'exécution est libéré et sert d'autres requêtes.

    using Exemple28.Dao;
using Exemple28.Data;
using Exemple28.Entities;
using Microsoft.EntityFrameworkCore;
using MySqlConnector;

namespace Exemple28.Metier;

public record DonneesPersonne(string Prenom, string Nom, int Age);

// la couche MÉTIER : les règles de gestion, et elles seules
public class PersonnesMetier(PersonnesDao dao, PersonnesDbContext db)
{
    private const string Homonyme = "Une personne porte déjà ces prénom et nom.";

    public Task<List<Personne>> ListerAsync() => dao.ListerAsync();

    public async Task<Personne> LireAsync(int id) =>
        await dao.LireAsync(id) ?? throw new MetierException("Cette personne n'existe pas (ou plus).");

    public Task<Personne> AjouterAsync(DonneesPersonne donnees) =>
        TransactionAsync(async () =>
        {
            // règle 1 : pas deux personnes de mêmes prénom et nom
            if (await dao.HomonymeAsync(donnees.Prenom, donnees.Nom, 0) is not null)
            {
                throw new MetierException(Homonyme);
            }
            var personne = new Personne { Prenom = donnees.Prenom, Nom = donnees.Nom, Age = donnees.Age };
            return await dao.SauvegarderAsync(personne);
        });

    public Task<Personne> ModifierAsync(int id, int version, DonneesPersonne donnees) =>
        TransactionAsync(async () =>
        {
            var personne = await LireAsync(id);
            // règle 2 : on ne modifie pas une fiche modifiée entre-temps par un autre
            if (personne.Version != version)
            {
                throw new MetierException("Cette fiche a été modifiée entre-temps : rechargez-la.");
            }
            if (await dao.HomonymeAsync(donnees.Prenom, donnees.Nom, id) is not null)
            {
                throw new MetierException(Homonyme);
            }
            personne.Prenom = donnees.Prenom;
            personne.Nom = donnees.Nom;
            personne.Age = donnees.Age;
            return await dao.SauvegarderAsync(personne);
        });

    public async Task<Personne> SupprimerAsync(int id)
    {
        var personne = await LireAsync(id);
        await dao.SupprimerAsync(id);
        return personne;
    }

    // [travail] s'exécute dans une transaction : COMMIT s'il réussit, ROLLBACK
    // s'il lève une exception. Les erreurs de la base deviennent des MetierException
    private async Task<R> TransactionAsync<R>(Func<Task<R>> travail)
    {
        await using var transaction = await db.Database.BeginTransactionAsync(); // START TRANSACTION
        try
        {
            var resultat = await travail();
            await transaction.CommitAsync(); // COMMIT
            return resultat;
        }
        catch (DbUpdateConcurrencyException)
        {
            // l'UPDATE "WHERE id = ... AND version = ..." n'a modifié aucune ligne
            throw new MetierException("Cette fiche a été modifiée entre-temps : rechargez-la.");
        }
        catch (DbUpdateException e) when (e.InnerException is MySqlException { ErrorCode: MySqlErrorCode.DuplicateKeyEntry } erreurSql
                                          && erreurSql.Message.Contains("unq_personnes_prenom_nom"))
        {
            // deux ajouts simultanés : la contrainte d'unicité de la base a refusé le second
            throw new MetierException(Homonyme);
        }
        // toute autre exception poursuit son chemin ; la transaction, refermée
        // sans COMMIT par "await using", est annulée (ROLLBACK)
    }
}

    Commentons ce code :

    • ligne 9 : les données d'une personne, telles que la couche web les transmet ;
    • ligne 12 : la couche métier utilise le DAO, et le [DbContext] pour ouvrir des transactions. Tous deux sont des services [Scoped] : au cours d'une requête, le DAO et la couche métier reçoivent le même [DbContext], donc la même connexion et la même transaction. (Avec [TypeORM], il fallait passer à chaque méthode du DAO l'objet de la transaction) ;
    • lignes 18-19 : une personne absente est une [MetierException]. L'opérateur [??] fournit une valeur de remplacement ; [throw] peut en tenir lieu ;
    • lignes 21-30 : l'ajout, dans une transaction. Règle : pas deux personnes de mêmes prénom et nom. On la vérifie avant l'écriture pour donner un message clair ;
    • lignes 33-49 : la modification. Règle supplémentaire, le verrou optimiste (lignes 38-40) : le formulaire de modification a transporté la version de la fiche telle qu'elle était à l'ouverture du formulaire. Si elle a changé entre-temps (un autre utilisateur a modifié la même fiche), on refuse, plutôt que d'écraser silencieusement son travail ;
    • lignes 61-67 : [BeginTransactionAsync] ouvre une transaction ([START TRANSACTION]), [CommitAsync] la valide ([COMMIT]). [await using] referme la transaction à la sortie du bloc, quoi qu'il arrive : refermée sans [COMMIT], elle est annulée ([ROLLBACK]). Ainsi, une exception levée par [travail] (une [MetierException] comprise) annule tout ce qui a été fait ;
    • lignes 70-73 : la vérification de la version, plus haut, ne suffit pas toujours : deux utilisateurs peuvent enregistrer la même fiche au même instant, et passer tous deux la vérification. L'[UPDATE ... WHERE id = ... AND version = ...] du second ne modifie alors aucune ligne ; EF Core s'en aperçoit et lève une [DbUpdateConcurrencyException], qui devient la même [MetierException] ;
    • lignes 75-79 : de même, deux ajouts simultanés de la même personne passent la vérification des homonymes, mais la contrainte d'unicité de la base, elle, ne laisse rien passer. L'erreur [MySQL] (code [DuplicateKeyEntry], n° 1062) arrive enveloppée dans une [DbUpdateException] (propriété [InnerException]) ; son message cite le nom de la contrainte. La clause [when] n'intercepte l'exception que si la condition est vraie. [is MySqlException { ErrorCode: ... } erreurSql] est un filtrage par motif : il teste le type et la valeur d'une propriété, et range l'objet dans une variable.

    private string? nom;

    [Required(ErrorMessage = "Le prénom est obligatoire.")]
    [MaxLength(30, ErrorMessage = "30 caractères au plus.")]
    public string? Prenom { get => prenom; set => prenom = value?.Trim(); }

    [Required(ErrorMessage = "Le nom est obligatoire.")]
    [MaxLength(30, ErrorMessage = "30 caractères au plus.")]
    public string? Nom { get => nom; set => nom = value?.Trim(); }

    [Required(ErrorMessage = "L'âge est obligatoire.")]
    [Range(0, 150, ErrorMessage = "L'âge doit être compris entre 0 et 150.")]
    public int? Age { get; set; }

    // la version de la fiche, transportée par un champ caché (modification seulement)
    public int? Version { get; set; }
}

    public FormulairePersonne Valeurs { get; init; } = new();
    public Dictionary<string, string> Erreurs { get; init; } = new(StringComparer.OrdinalIgnoreCase);
}

    using Exemple28.Metier;
using Exemple28.Models;
using Microsoft.AspNetCore.Mvc;

namespace Exemple28.Controllers;

// la couche WEB : elle ne connaît que la couche métier
public class PersonnesController(PersonnesMetier metier) : Controller
{
    [HttpGet("/")]
    public IActionResult Accueil() => RedirectToAction(nameof(Liste));

    [HttpGet("personnes")]
    public async Task<IActionResult> Liste()
    {
        return View(await metier.ListerAsync());
    }

    [HttpGet("personnes/ajout")]
    public IActionResult Ajout() => Formulaire(Vue("Ajouter une personne", "/personnes/ajout", new()));

    [HttpPost("personnes/ajout")]
    public async Task<IActionResult> Ajouter(FormulairePersonne saisie)
    {
        var vue = Vue("Ajouter une personne", "/personnes/ajout", saisie);
        if (!ModelState.IsValid)
        {
            return Formulaire(vue);
        }
        try
        {
            var personne = await metier.AjouterAsync(new DonneesPersonne(saisie.Prenom!, saisie.Nom!, saisie.Age!.Value));
            TempData["Succes"] = $"{personne.Prenom} {personne.Nom} a été ajouté(e).";
            return RedirectToAction(nameof(Liste));
        }
        catch (MetierException e)
        {
            // une règle métier refuse : on réaffiche le formulaire, le message en bas de page
            return Formulaire(vue, e.Message);
        }
    }

    [HttpGet("personnes/{id:int}/modification")]
    public async Task<IActionResult> Modification(int id)
    {
        try
        {
            var p = await metier.LireAsync(id);
            var valeurs = new FormulairePersonne { Prenom = p.Prenom, Nom = p.Nom, Age = p.Age, Version = p.Version };
            return Formulaire(Vue("Modifier une personne", $"/personnes/{id}/modification", valeurs));
        }
        catch (MetierException e)
        {
            TempData["Erreur"] = e.Message;
            return RedirectToAction(nameof(Liste));
        }
    }

    [HttpPost("personnes/{id:int}/modification")]
    public async Task<IActionResult> Modifier(int id, FormulairePersonne saisie)
    {
        var vue = Vue("Modifier une personne", $"/personnes/{id}/modification", saisie);
        if (!ModelState.IsValid)
        {
            return Formulaire(vue);
        }
        try
        {
            var donnees = new DonneesPersonne(saisie.Prenom!, saisie.Nom!, saisie.Age!.Value);
            var personne = await metier.ModifierAsync(id, saisie.Version ?? 0, donnees);
            TempData["Succes"] = $"{personne.Prenom} {personne.Nom} a été modifié(e).";
            return RedirectToAction(nameof(Liste));
        }
        catch (MetierException e)
        {
            return Formulaire(vue, e.Message);
        }
    }

    [HttpPost("personnes/{id:int}/suppression")]
    public async Task<IActionResult> Supprimer(int id)
    {
        try
        {
            var personne = await metier.SupprimerAsync(id);
            TempData["Succes"] = $"{personne.Prenom} {personne.Nom} a été supprimé(e).";
        }
        catch (MetierException e)
        {
            // pas de formulaire à réafficher : l'erreur voyage elle aussi dans TempData
            TempData["Erreur"] = e.Message;
        }
        return RedirectToAction(nameof(Liste));
    }

    // le modèle de la vue du formulaire, avec les erreurs de ModelState rangées par champ
    private FormulaireVue Vue(string titre, string action, FormulairePersonne valeurs) => new()
    {
        Titre = titre,
        Action = action,
        Valeurs = valeurs,
        Erreurs = ModelState
            .Where(c => c.Value!.Errors.Count > 0)
            .ToDictionary(c => c.Key, c => c.Value!.Errors[0].ErrorMessage, StringComparer.OrdinalIgnoreCase),
    };

    private ViewResult Formulaire(FormulaireVue vue, string? erreur = null)
    {
        ViewData["Erreur"] = erreur;
        return View("Formulaire", vue);
    }
}

    Commentons ce code :

    • ligne 8 : le contrôleur ne connaît que la couche métier ;
    • ligne 11 : la racine du site redirige vers la liste ;
    • lignes 14-16 : une action asynchrone : elle rend un [Task<IActionResult>], et attend ([await]) la liste lue en base ;
    • lignes 23-39 : l'ajout, en trois temps : validation du formulaire (erreurs : réaffichage), appel de la couche métier (succès : message dans [TempData] et redirection, cf. exemple 20), [MetierException] (réaffichage avec le message en bas de page). Une autre exception n'est pas interceptée : c'est une anomalie, qui produira une erreur 500 ;
    • lignes 44-55 : le formulaire de modification, prérempli avec la fiche lue en base, y compris sa version ;
    • lignes 60-76 : même schéma que l'ajout ; la version renvoyée par le formulaire est transmise à la couche métier ;
    • lignes 81-93 : la suppression. Il n'y a pas de formulaire à réafficher : une éventuelle erreur voyage, elle aussi, dans [TempData] ;
    • lignes 97-104 : le modèle de la vue du formulaire, avec les erreurs de [ModelState] rangées par champ (cf. exemple 19).
